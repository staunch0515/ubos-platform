# Comparison: AI Integration

## 1. Question

How does AI take part in the platform? This covers AI as the builder of metadata and logic, as a runtime capability for logic, as a user-facing copilot, as a semantic search layer and as a translator. What guardrails make this safe?

## 4. Analysis

- **Common precondition.** Every AI proposal in the corpus depends on the same property: all artifacts are small, typed, versioned JSON entities behind a narrow, stable API. This lets an AI read the meta-model, generate valid bundles, and have them validated, sandboxed, reviewed and reverted.
- **The roles are complementary:**
  - builder (UP, UB);
  - runtime capability (UC);
  - agent (UC);
  - copilot (UP, UC, US);
  - semantic memory (UB);
  - explainer (US).
- **Guardrails** come from other topics:
  - meta-schema validation (VRD-02-02);
  - rule and decision vetoes (VRD-09-05);
  - sandbox (VRD-05-03);
  - drafts and approvals (VRD-08-03, VRD-10-04);
  - provenance (VRD-04-05).
- **Provider neutrality.** UB and UC agree that "UBOS uses a brain, it does not host one": LLMs are external services configured as entities.

## 5. Verdicts

### VRD-16-01 — AI as builder through the same governed path as humans (fusion UP + UB + US)
- **Decision:** fusion.
- **Consequences:**
  - The AI builder reads the meta-model (types, UODS meta-schema, slot catalogue, existing entities) through query and URI.
  - It produces an entity bundle (types, logic, views, actions, seed data).
  - The kernel dry-runs the bundle: meta-schema, compile, rule checks and optional test pipelines.
  - Accepted bundles are committed to a draft branch; publishing follows the approval policy.
  - Rejections return structured, path-level errors for self-correction.
  - Commits record `author = ai:<agent>` and the prompt or process reference.

### VRD-16-02 — AI as a runtime capability via syscalls (best-of UC)
- **Decision:** best-of UC.
- **Consequences:**
  - `ai.chat`, `ai.embed`, `ai.classify` and `ai.extract` are syscalls.
  - Provider, model, endpoint and key come from an `AiProvider` config entity per context; the key is stored hashed or as an external secret reference.
  - Calls are policy-checked, metered (process log app/billing, CON-UB-043) and logged.

### VRD-16-03 — Agents are identities with Contexts and memory (best-of UC)
- **Decision:** best-of UC.
- **Consequences:** An agent is a `User` of kind agent, with roles and a Context holding memory (VRD-07-04). It acts only through actions and protocol operations, so all of its work is audited and policy-bound.

### VRD-16-04 — Copilot turns natural language into intents, never into direct writes (fusion US + UC + UW)
- **Decision:** fusion.
- **Consequences:**
  - The copilot maps NL to `Emit`/`Query` messages or client intents, which it shows before execution when they are effectful.
  - UI instructions follow the zone/registry contract (CON-UC-058).

### VRD-16-05 — Semantic memory: embeddings per version (→ VRD-12-04) and RAG over the meta-model (adapt UB)
- **Decision:** adapt UB; embeddings as in VRD-12-04.

### VRD-16-06 — Explanations from audit traces (best-of US design)
- **Decision:** best-of US design.
- **Consequences:** "Why" questions are answered from the process lineage, execution node tree and rule decisions (CMP-21). The AI summarises recorded facts and does not guess.

### VRD-16-07 — AI-native i18n (adapt UB)
- **Decision:** adapt UB.
- **Consequences:** Only source-language labels are authored. Missing translations are generated on demand as `I18n` entities with a `source_hash`; they are editable and invalidated when the source changes.
