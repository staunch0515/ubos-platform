# Comparison: Development Method and AI-assisted Engineering

## 1. Question

How is the platform built and extended, by people and by AI coding agents? This covers repository conventions, instruction files, delivery units, tests and staging. The resulting specification is meant to be read by AI.

## 2. Candidates

| KEY | Approach | Refs | Summary |
|---|---|---|---|
| UP | One concept per migration; AI Architect writes logic | CON-UP-043, 061 | Small increments |
| LC | Coding rules (logger only, English-only comments, no Chinese in code); data-driven test cases (JSON lists of process calls); conversational requirements → generated apps | CON-LC-053, 061, 063, HL-LC-010 | Tests as data |
| UB | House-rule prompts for IDE assistants (SLF4J, constructor injection, CAS/micro-commit patterns, metadata-driven resolution) | CON-UB-067 | Standards in prompts |
| UC | Stage-by-stage build log (one stage = goal, code, verification); handoff documents across chat sessions; `prompt.md` house rules (6 tables, `logrums`, explicit `_extends`, files ≤ 100 lines, complete files, no Chinese in code) | CON-UC-002, 065, HL-UC-014 | Prompt-driven development |
| US | "Three-piece set" delivery (Action JSON + generator + submitter); CLI `.rhai` scenarios; source bundling for AI context | CON-US-004, 063, 065, HL-US-010, 012 | Feature packaging |
| LS | `claude.md` repository instruction file (rules, core logic, design) | CON-LS-063, HL-LS-011 | Stable AI contract |
| UW | Generated by an AI app builder | CON-UW-061 | – |

## 3. Analysis

- **All repositories except FU were built with AI assistance.** Four practices recur:
  - (1) a stable **instruction file** with house rules (UC `prompt.md`, LS `claude.md`, UB prompts, LC rules);
  - (2) **small verified increments** (UC stages, UP migrations);
  - (3) **features as data packages**, generated and reviewed as a unit (US three-piece set, UB AI bundles);
  - (4) **executable scenarios** written in the platform's own language (LC JSON process calls, US `.rhai`).
- **Recurring failures** in the corpus come from missing shared context:
  - vocabulary drift (Logrum → Workspace → Job);
  - duplicate conventions (`master`/`main`, `commit`/`cid`);
  - uncompiled design sketches (LS);
  - legacy id formats after migrations (UC).
- These failures are what this documentation set (ID registry, glossary, conventions, AI-GUIDE) is meant to prevent.

## 4. Verdicts

### VRD-22-01 — Repository instruction file and conventions are part of the spec (fusion UC + LS + UB + LC)
- **Decision:** fusion.
- **Consequences:**
  - P3 produces conventions: naming, IDs, language rules (English in code), logging, file size, and the no-new-tables rule.
  - P5 turns `AI-GUIDE.md` into the canonical instruction file for implementing agents.
  - Implementation repositories include it as `CLAUDE.md` / `AGENTS.md`.

### VRD-22-02 — Delivery unit = package of entities with scenarios (fusion US + LC + UB)
- **Decision:** fusion.
- **Consequences:**
  - A feature ships as a package (VRD-17-01) containing types, actions (with transitions), logic, views and seed data.
  - It also contains **scenario files**: ordered protocol messages (`Mutate`/`Emit`/`Query`) with expected results, runnable by the CLI.

### VRD-22-03 — Staged construction with verification per step (best-of UC)
- **Decision:** best-of UC.
- **Consequences:** The P4 spec orders chapters by dependency. Each chapter's acceptance section lists verifiable criteria, so an implementing agent can build and verify one chapter at a time.

### VRD-22-04 — One vocabulary (NEW)
- **Decision:** NEW.
- **Consequences:**
  - The P3 glossary fixes every term: Entity, Type, Context, Process, Job, Action, Logic, Behavior, Slot, Package, etc.
  - Each term records its corpus aliases (e.g. Logrum → Context/Job; Workspace → Context; SysFunction → Logic).
  - Implementations must not introduce synonyms.
