> 对象：产品负责人 · 日期：2026-09-29 · 仓库：`staunch0515/ubos-unit`（原 `ubos-platform` 分支 `claude/gifted-edison-cmqbu9`）

## 一、一句话概括

UBOS 把"业务状态如何随时间变化"做成一个公开标准（BPA）：
- 业务状态有类型、可继承、像代码一样有版本、有双时间维度、受规则治理、能用密码学证明；
- 人和 AI 代理都只能通过同一条"可审阅、可模拟、可撤销"的路径去改变它。

标准运行在参考内核 DVM 上，每一份合同或订单都是一个标准的"业务处理单元"（BPU）。

**核心原则：机制硬化，策略软化。**
- 内核语义固定、有版本、可验证；
- 业务行为（类、规则、流程、视图）全部是可版本化的数据，以业务包（Buk）的形式交付。

按你的要求，"公司的终结""意图经济""算力货币"这三类长期叙事被明确排除在范围之外（规格书约束 CST-008），不会以任何需求、功能或阶段出现。

## 三、要解决的问题与价值

**现状的三类工具各有缺陷：**
- **套装软件 / SaaS**：历史被覆盖，定制要么分叉，要么等厂商。
- **低代码平台**：规则没有版本纪律，不能先在真实数据上试运行。
- **Office 文档和表格**：是死快照，公式不透明，没有可信历史。

**两股新压力：**
- 监管要求可复现：某个日期知道什么、谁改的、按哪条规则改的。
- AI 代理进入业务运营后，企业不敢让它直接改记录系统。

**八条产品原则：**
1. 机制硬化、策略软化；
2. 历史永不改写；
3. 每个变更生效前可审阅；
4. 每个结果可解释；
5. 每个状态可证明；
6. 本地优先、数据可迁移；
7. 渐进披露：业务用户看不到"分支、合并"这类平台术语；
8. 系统边界一律用开放标准。

**首个业务包**是美国标准的基础财务系统（DEC-022）：总账与科目表、带审批的凭证、会计期间与结账、应收、应付（含 1099）、银行对账、固定资产、多币种（ASC 830）、基本州销售税、四张财务报表、审计轨迹与内控。只支持单一公司。基金运营和合同管理标为"推迟"，编号保留。

这套软件**不销售**（DEC-023），目的是展示平台强加给每个业务包的能力（版本历史、制单与复核、"按当时所知"查询、模拟、证据、解释），并与你的 Java 系统按同一份财务需求做对比（DEC-026）。

## 四、13 个系统及分层

| 层 | 系统 | 作用 |
|---|---|---|
| 标准层 | **BPA** 标准治理 | 标准文本、测试向量、形式化模型、变更流程、认证计划 |
| | **FRG** Logic Forge | 开发与验证工具链：检查、类型生成、测试、模拟、打包签名、一致性测试运行器 |
| 内核层 | **DVM** 参考内核 | 存储、模型、版本、双时间、账本、事务、运行时、规则、授权、查询、证明 |
| 宿主层 | **NOD** 节点 | 把内核变成可运行的系统，有 Box / Server / Cell / Worker 四种形态 |
| | **SDK** | 客户端访问 UBOS 的唯一途径（Rust、TypeScript，之后 Python） |
| 平台服务层 | **CTL** 控制平面 | 集群、租户放置与迁移、升级批次、计量计费；**看不到业务数据** |
| | **EXC** Buk 市场 | 发布、可复现验证、许可证、法币开票与分成 |
| | **NTY** 公证 | 外部时间戳锚定、证据包、开源独立校验器 |
| | **BRG** 桥接 | 数据迁移、批量集成、分析出口（Iceberg、DuckDB） |
| | **FED** 联邦 | 跨组织的身份注册、信任关系、共享 BPU |
| 智能层 | **AGT** 代理中心 | 模型网关、代理运行时、工具/MCP、Copilot、AI 构建器 |
| 体验层 | **WSP** 工作台 | 服务端驱动的界面、Office 类功能、电子签名、桌面和移动端 |
| | **STU** Studio | 建模和规则编辑、变更集审阅、模拟、发布 |

**关键架构规则：**
- 下层不依赖上层；
- 只有提交路径能写权威状态；
- 内核是纯库，不做任何 I/O；
- 全系统只有一个授权引擎；
- AI 输出一律视为不可信输入；
- 控制平面对业务数据"失明"。

**技术栈：**
- Rust（内核、服务端、CLI）、TypeScript（Web）、Tauri 2（桌面和移动端）；
- PostgreSQL 作为存储（SQLite 推迟到 PH-4，DEC-024），S3 兼容对象存储；
- Rhai 脚本 + WASM 组件作为逻辑运行时；
- Cedar 类策略语言做授权。

## 五、标准（BPA）的核心内容

- **对象与存储**
  - 内容寻址：RFC 8785 规范 JSON + SHA-256；
  - 大内容分块；
  - 字段级加密，通过"销毁密钥"实现合规删除，且删除后证明仍然成立。
- **类体系**：单根继承 + trait，C3 线性化，子类只能收窄、不能放宽，多态端口，透镜（lens）式的模式演进。
- **四种状态类型**：Definition（定义）、Ledger（账本，只追加、序号无空洞、复式记账）、System（系统）、RawDocument（原始文档）。
- **版本**
  - 提交、分支、变更集（内容变化后审批自动失效）；
  - 三方合并，账本条目在合并时追加、不合并；
  - 回滚、分支间继承、标签和发布。
- **双时间**：有效时间与事务时间分离；四种时间线编辑操作；可在任意历史时点查询；追溯变更的影响分析与重述。
- **事务**：单次原子刷写；对象级比较并交换；可选可串行化；幂等键；outbox；延迟提交（审批）；批量处理；saga。
- **证明**：每次提交生成一个 Merkle 根，结果与操作顺序无关；Ed25519 签名；包含证明与一致性证明；外部锚定；证据包；文档封印。
- **指令集 ABI 1.0**：7 大类 30 条指令；5 种执行配置；所有非确定性输入写入日志，可精确重放。
- **治理规则表**：类似 CSS 的层叠规则（锁定 > 层 > 特异性 > 优先级 > 位置），决策表，可解释。
- **协议**：UBTP 客户端协议；同步协议（范围树、设备分支）；联邦回退；共享 BPU。
- **一致性与认证**：与实现语言无关的测试向量、适配器协议、带签名的测试报告、"BPU Compliant"认证。

## 六、六个阶段：目的、内容与验证方式

所有阶段遵守同一套规则：
- 退出准则全部有证据才能结束，不按日期结束；
- 回归测试只增不减；
- "必须"级需求不许顺延；
- 退出由阶段验收委员会签署，并记为一条决策记录。

## 七、验证体系（本次重点）

1. **12 种验证方法**：
   - 测试向量与一致性测试（CONF）；
   - 性质测试（PROP）、确定性模拟（SIM）、形式化模型（FORM）；
   - 真实故障注入（FAULT）；
   - 端到端场景（SCN）、基准测试（BENCH）、安全评估（SEC）；
   - 可用性研究（USE）、审查（INSP）、外部验收演练（PILOT，如 PH-3 的注册会计师审计演练）。

   每种方法都写明了步骤、工具、证据和默认通过标准。
2. **统一编号**：验证项编号按方法 + 系统或阶段分段。标准向量按条款区域编号（VER-CONF-0001…6299），系统级测试从 7000 起。校验器会检查编号区间不重叠。
3. **90 个验证项**覆盖全部 78 条有效退出准则（7 条已作废，编号保留）。每项写明要验证什么、在哪个环境和数据集上、操作步骤、通过标准和证据；校验器强制"每条退出准则至少有一个验证项支撑"。
4. **自动追溯矩阵**：需求 → 实现它的设计项或标准条款 → 验证它的测试套件 → 阶段退出准则。首次运行发现 60 条"必须"级需求没有覆盖，已通过补关联和新增 8 条设计项全部补齐；现在每个阶段的"必须"级缺口为 0。
5. **参考环境与数据集**：7 个参考环境；财务负载 WL-FIN-M；示例公司 Northwind Components, Inc. 的账套和经会计复核签字的预期结果；以及沙箱逃逸、租户隔离、提示注入、证据篡改等对抗性测试集。

## 九、主要风险（节选）

| 风险 | 应对 |
|---|---|
| PostgreSQL 达不到提交延迟目标 | PH-0 实测；组提交；日志结构层作为预案 |
| 跨平台结果不确定 | 三平台每晚重放；十进制数测试向量；固定时区数据库版本 |
| PH-1 范围过大 | 两个关卡；每周进度追踪；"应该"级需求经决策可顺延 |
| 业务用户看不懂分支概念 | 渐进披露；隐藏平台术语；第 3、6 个月各做一次可用性测试 |
| 会计错误未被发现（舍入、汇率重估、期间截止、1099 门槛） | 预期结果独立计算并由会计复核签字；借贷平衡性质测试；每个场景都做报表勾稽 |
| 与 Java 系统的对比不对等 | 同一份需求、同一个示例公司、同一套记录协议；范围差异逐条登记 |
| 提示注入导致副作用 | 数据标记、权限范围限制、高风险操作必须人工确认、注入测试集纳入持续集成 |
| 第三方生态冷启动 | 伙伴计划、收入分成、第一方模板 |

## 十、如何使用这套规格书

- **给 AI 或新工程师**：先读 `00-meta/05-ai-reading-guide.md`。它按任务给出阅读路线，并说明冲突时的优先级：标准条款 > 合规需求 > 非功能需求 > 功能需求 > 架构规则 > 设计要求。
- **查任意编号**：`INDEX/` 目录下的自动生成索引。
- **一键重新生成并校验**：`docs/tools/regen_all.sh`，结果必须为 0 错误。
- **修改规则**：编号永不重编；需求换阶段必须记一条决策；"必须"级缺口必须保持为 0。
